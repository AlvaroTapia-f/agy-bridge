# Exploration: custom-opencode-provider-agy-bridge

## Current State

**agy-bridge** (`agy-bridge.ts`, 1178 lines, Deno 2.9.5, single-file service) exposes an OpenAI-compatible HTTP API on `127.0.0.1:7421` (configurable via `PORT`, `HOSTNAME`). It spawns the official `agy` binary per request with `stream-json` protocol; never talks to Google directly. Key contract:

- **Endpoints:** `GET /v1/models` (and `/models`), `POST /v1/chat/completions` (and `/chat/completions`), `GET /healthz` / `/v1/healthz`. Health is unauthenticated; all other routes pass `accessGuard()`.
- **Auth:** `AGY_TOKEN` env var (generated by `install.sh` to `~/.config/agy-bridge/env`, `chmod 600`). Guard enforces `Authorization: Bearer <AGY_TOKEN>` when set; empty disables check (dev only). Also enforces `Host` header `127.0.0.1:*` or `localhost:*` (DNS-rebinding protection).
- **Models:** Dynamic list via `agy models` (TSV `slug<TAB>display`), cached in `modelSlugs`, refreshed on every `GET /v1/models`. Fallback list of 14 slugs in `FALLBACK_MODELS` (`gemini-3.7-flash-{high,medium,low}`, `gemini-3.6-flash-{high,medium,low}`, `gemini-3.5-flash-{high,medium,low}`, `gemini-3.1-pro-{high,low}`, `claude-sonnet-4-6`, `claude-opus-4-6-thinking`, `gpt-oss-120b-medium`). Additionally `parseAutoModel()` supports autonomous delegation: `auto-<profile>-<realModel>` where `profile ∈ {ro,rw}` maps to agy agents `worker-ro` / `worker-rw`. The real suffix is validated against `modelSlugs`.
- **Request handling:** `model` field validated against `modelSlugs` (or suffix for auto-). Prompt is rendered to `prompt` string, sent via stdin NDJSON `{event:"user",message:{content:prompt}}` to avoid Linux `E2BIG` (verified 190KB). Tools are rendered as `<tool_call>`/` <tool_result>` text protocol when `AGY_TOOLS=on`.
- **Ops:** systemd template `agy-bridge.service.template` uses `EnvironmentFile=%h/.config/agy-bridge/env`, `ExecStart=${DENO_BIN} run --allow-net=127.0.0.1 --allow-run=${AGY_BIN} --allow-write=%h/.local/state/agy-bridge --allow-read=%h/.gemini/antigravity-cli/brain --allow-env`. `install.sh` auto-detects `deno`/`agy`, generates `AGY_TOKEN` via `openssl rand -hex 24`.

**opencode** (v1.18.23, `~/.config/opencode/opencode.json`, schema `https://opencode.ai/config.json`): No `provider` key currently configured (fresh install, `opencode.json` contains only `agent`/`mcp`/`permission`). Auth is stored separately in `~/.local/share/opencode/auth.json` (currently only `opencode-go` entry). Provider docs (`https://opencode.ai/docs/providers`) confirm:

- Providers are declared under top-level `provider` object in `opencode.json`. Per `ProviderConfig` (from `https://opencode.ai/config.json` schema): keys `npm`, `name`, `id`, `options: { baseURL, apiKey, headers, timeout, ... }`, `models: { <modelId>: { name, limit, variants, headers, ... } }`, `whitelist`/`blacklist`, `env`.
- For any OpenAI-compatible service, use `npm: "@ai-sdk/openai-compatible"` (chat/completions) or `@ai-sdk/openai` for `/v1/responses`. Custom provider requires: `/connect` → `Other` → enter `providerId` → enter API key (stored in `auth.json` under that id, type `api`), plus a `provider` entry in `opencode.json` with `npm`, `name`, `options.baseURL`, `models`.
- `options.apiKey` can be literal or env-var reference `"{env:VAR}"` (docs example shows `"{env:ANTHROPIC_API_KEY}"`). Alternatively `options.headers.Authorization` can be set. When `apiKey` is set, the AI SDK sends it as `Authorization: Bearer <key>` automatically.
- `models.*.variants` is a map `variantName -> {disabled?}` that feeds the `model-variants` plugin (`~/.config/opencode/plugins/model-variants.ts`), which calls `input.client.provider.list()` and caches `~/.gentle-ai/cache/model-variants.json` for the effort picker. Agent config also has a top-level `variant` field for default effort per agent.
- No repo-local `opencode.json` exists in `agy-bridge` (`ls` shows no such file); global config is the source of truth lost on clean install.

## Affected Areas

- `agy-bridge.ts` — already implements `GET /v1/models` dynamic vs `FALLBACK_MODELS`; any change to model naming (e.g., exposing variants as distinct ids vs base+variant) affects `modelSlugs` validation and `parseAutoModel` mapping. No code change required for opencode integration unless a variant-to-suffix translation layer is added.
- `~/.config/agy-bridge/env` — source of `AGY_TOKEN`; must be propagated to opencode's `auth.json` or `options.apiKey`. Permissions `600` must not leak into repo.
- `~/.config/opencode/opencode.json` — needs new `provider.agy-bridge` entry (global, not repo-local unless project-specific). Global file currently 119KB, no provider section; edit must preserve schema.
- `~/.local/share/opencode/auth.json` — new key `agy-bridge: {type:"api", key:"<AGY_TOKEN>"}` when using `/connect Other` flow; file is `600` (`rw-------`).
- `~/.config/opencode/plugins/model-variants.ts` — already handles `variants` extraction; no change, but confirms effort support is via `models.<id>.variants`.
- `install.sh` / `agy-bridge.service.template` / `.env.example` — documentation must reference the new provider setup; `install.sh` already generates `AGY_TOKEN` but does not configure opencode (gap the change will fill).
- `openspec/changes/custom-opencode-provider-agy-bridge/*` — new proposal/spec/design artifacts will live here.

## Approaches

### 1. Static `opencode.json` provider entry + `/connect Other` auth (RECOMMENDED)

Define a custom provider `agy-bridge` in `~/.config/opencode/opencode.json` with `npm: "@ai-sdk/openai-compatible"`, `options.baseURL: "http://127.0.0.1:7421/v1"`, and a `models` map enumerating every bridge model (including effort suffixes as distinct ids, e.g., `gemini-3.7-flash-high`). Auth stored via TUI `/connect` → `Other` → `agy-bridge` → paste `AGY_TOKEN` (writes to `auth.json`). Alternatively set `options.apiKey: "{env:AGY_TOKEN}"` and export `AGY_TOKEN` from `~/.config/agy-bridge/env` in shell profile.

- Pros: Official documented pattern; secret stays out of `opencode.json` (in `auth.json` 600); minimal code; `opencode models` will list models; works with existing bridge `baseURL` and `Authorization: Bearer` guard; survives `agy models` changes only with manual sync.
- Cons: Model list is static — drifts if `agy models` adds/removes slugs; must manually maintain effort variants as separate model ids (14 entries) or decide on `variants` grouping; env-var form requires user to `set -a; source ~/.config/agy-bridge/env; set +a` before launching `opencode` (systemd bridge already has it, but opencode TUI does not inherit it).
- Effort: **Low** — single JSON edit + one-time `/connect` step; document in README/install.sh.

Example shape (from docs):
```json
{
  "provider": {
    "agy-bridge": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "AGY Bridge",
      "options": { "baseURL": "http://127.0.0.1:7421/v1" },
      "models": {
        "gemini-3.7-flash-high": { "name": "Gemini 3.7 Flash High" },
        "gemini-3.7-flash-medium": { "name": "Gemini 3.7 Flash Medium" }
      }
    }
  }
}
```

### 2. Base-model + `variants` grouping (effort as variant)

Define fewer base models (e.g., `gemini-3.7-flash`) and attach `variants: { "high": {}, "medium": {}, "low": {} }` per model. The `model-variants` plugin already surfaces variant keys to the picker. Agents could set `model: "agy-bridge/gemini-3.7-flash", variant: "high"`.

- Pros: Cleaner picker (3 models vs 9 entries for 3.7/3.6/3.5 flash); aligns with opencode's native effort UX (variant picker); matches user request “provider must have models and efforts” semantically.
- Cons: Bridge does NOT understand `variant` field — it only reads `model` string from the OpenAI request. Variant selection currently does NOT mutate the `model` id sent over the wire (opencode keeps base id; variant is metadata for temperature/tools, not suffix). Therefore `agy-bridge` would receive `gemini-3.7-flash` without suffix and reject it (`unknown model`). To make this work, need a translation layer: either a custom opencode plugin that rewrites `model` to `${model}-${variant}` before request, or a bridge change to accept bare base models and map variant header to effort. Both are extra code and brittle.
- Effort: **Medium-High** — requires plugin or bridge patch and testing of `input.client.provider.list()` variant propagation.

### 3. Dynamic plugin auto-discovery

Write a small opencode plugin (`~/.config/opencode/plugins/agy-bridge.ts`) that on startup fetches `GET http://127.0.0.1:7421/v1/models` (with `Authorization: Bearer` from `auth.json` or env) and registers models programmatically via the SDK, rather than static JSON.

- Pros: Always in sync with `agy models` output; no manual JSON maintenance; can also auto-generate `auto-ro-*`/`auto-rw-*` combinations (28 extra ids) if desired.
- Cons: Non-standard vs docs; plugin must handle auth header injection, retry, and `Host` guard; still needs `provider` base entry; more surface to maintain; debugging harder (plugin load order, `refreshVariantsCache` timing). Effort picker still needs `variants` if efforts are desired as picks.
- Effort: **Medium** — new plugin file, Deno/Node interop, error handling for bridge down.

## Recommendation

**Approach 1** as the primary implementation for this change: static `provider` entry with flat model ids per effort suffix, authenticated via `/connect Other` → `auth.json`. It is the only approach verified against both the bridge's `accessGuard` + `FALLBACK_MODELS` contract and the official opencode custom-provider docs, and it meets the user's stated requirements exactly: “provider must have model names and efforts, and an apikey passed each time opencode uses it.” Efforts are represented as distinct model ids (`-high`/`-medium`/`-low` suffix) which opencode already lists as separate models — this matches how `FALLBACK_MODELS` are defined today and avoids the variant-translation gap noted in Approach 2. Approach 2 can be offered as a follow-up enhancement if a variant rewrite plugin is later added; Approach 3 as optional automation once static entry is proven.

## Risks

- **Auth leakage:** Putting `AGY_TOKEN` literal in `opencode.json` would commit a secret if that file is ever copied to a repo-local `opencode.json`. Mitigate by using `/connect Other` (token in `auth.json` 600) or `"{env:AGY_TOKEN}"` with sourcing from `~/.config/agy-bridge/env` (already 600). Never commit token to git.
- **Model drift:** `FALLBACK_MODELS` is 14 entries but `agy models` output can change; static `models` map requires manual update. If not updated, opencode will offer stale ids that bridge rejects (`unknown model`). Mitigate with a note to re-run `curl http://127.0.0.1:7421/v1/models -H "Authorization: Bearer $AGY_TOKEN"` after `agy` updates.
- **Effort naming collision:** Bridge suffixes `-high`/`-medium`/`-low` vs opencode `variants` keys — flat ids avoid collision but duplicate display names; variant grouping would mask the collision until runtime failure (bridge 400).
- **BaseURL nuance:** Bridge serves both `/v1/chat/completions` and `/chat/completions`; docs example uses `https://api.myprovider.com/v1`. Must ensure `baseURL` ends with `/v1` (not naked host) so the SDK appends `/chat/completions` correctly. Wrong baseURL yields 404.
- **Loopback-only + env propagation:** Bridge binds `127.0.0.1` and guards `Host`; opencode must not use a proxy. Also the systemd `EnvironmentFile` is not visible to the TUI process — user must export `AGY_TOKEN` separately if using `"{env:AGY_TOKEN}"` form; auth.json path avoids this.
- **Concurrency:** `MAX_CONCURRENT=1` — opencode parallel sessions will queue; not a config risk but UX expectation (latency 2-7s per turn) should be documented.
- **Variants cache:** `model-variants.ts` caches on startup; if `variants` are introduced later, cache file `~/.gentle-ai/cache/model-variants.json` must be refreshed (restart opencode).
